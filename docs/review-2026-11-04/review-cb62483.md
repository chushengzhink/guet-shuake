## P1：应优先处理

### R01 — 列表 Cookie 导入必然触发 NameError

位置：`guet/transport.py:183`，调用链见 `guet/session.py:303`。

`_import_cookies()` 使用不在其作用域中的 `rt.user_agent`。当前 `cookies_from_profile()` 返回 Cookie 字典列表，非空列表导入后必然走到该语句。用户提供的 `/api/courses` 堆栈与此一致，默认 HTTP 模式的客户端创建也受影响。

离线复现：用一个包含 name/value/domain/path 的虚拟 Cookie 构造 `HttpTransport`，得到 `NameError: name 'rt' is not defined`。另一个相关问题是空 Cookie 和 Mapping 分支提前返回，根本不会设置这里的自定义请求头。

建议验收：列表、Mapping、空 Cookie 三种构造路径均成功，且请求头不依赖 Cookie 类型。仅把 `rt` 改为 `self.rt` 不能覆盖后一个问题。

### R02 — 实时模式重新规划缺口时崩溃

位置：`guet/realtime.py:185`。

`LaneJob._advance()` 使用另一个方法 `step()` 的局部变量 `end`、`start`。当本轮上报后仍未达标，复查仍存在缺口时，会触发未定义变量错误，整门课程可能因此退出。

离线复现：60 秒任务，假服务端接收上报但暂不记入进度，重新规划时得到 `NameError: name 'end' is not defined`。

建议验收：上报暂未记账、复查仍有缺口的路径应能有限重试，并产生明确终态。

### R03 — 课程执行异常被汇总为成功

位置：`guet/scheduler.py:236`、`guet/scheduler.py:245`；消费方：`guet/gui/server.py:431`。

逐课程异常处理设置 `outcome.error` 后直接退出循环，随后仍用已有结果中是否包含 failed 来计算 `outcome.ok`。第一门课程抛异常时，`all([])` 为 True；前面课程成功、后面课程异常时也会误判。GUI 只检查 `not o.ok`，因此可能不展示该错误；CLI 成功判定也会受到影响。

离线复现：令 `AccountRunner.run_course()` 抛出 `RuntimeError('offline course failure')`，实际得到：

```json
{"ok": true, "error": "RuntimeError: offline course failure", "results": {}}
```

真实函数还会打印“全部成功，成功 0 失败 0”。建议验收：保留已完成课程结果，同时任何课程异常都必须使账号结果为失败。

## P2：功能和边界问题

### R04 — GUI 数字并行路数无法提交

位置：`guet/gui/web/index.html:400`、`guet/gui/server.py:378`、`guet/config.py:430`。

前端发送输入框 `.value`，值是字符串；后端 `_check_lanes()` 接受整数和 auto/all/max，却拒绝数字字符串。测速推荐给输入框赋数字后，读取 `.value` 仍是字符串，所以推荐流程同样受影响。

离线调用 `api_start(..., lanes='8')` 得到 `ConfigError`。建议验收：输入 8、测速推荐数字、auto/all、边界及非法值应在前后端采用一致语义。

### R05 — 不等长缺口的实时计时使用了上一段长度

位置：`guet/realtime.py:145`。

上报后把下一次执行时间设为 `now + 本次段长`，但下一段可能长度不同。碎片缺口会因此提前或延后上报，违背实时模式的时间语义。

离线复现：总时长 200 秒，已覆盖 `[10,100]`，剩余 `[0,10]` 和 `[100,200]`，chunk=100。虚拟时钟实际只推进 20 秒就返回 done，而剩余播放量为 110 秒。反过来先长后短会多等。

建议验收：相邻缺口长度不同、末尾短段及断点恢复均按即将上报的段长等待。

### R06 — 实时模式重复收到时长限制会无限重试

位置：`guet/realtime.py:125`。

只要异常中可解析出单段上限，就修改 chunk 并在 10 秒后重试，不判断是否真正缩小段长，也不增加重试次数。服务端在当前段长下继续返回相同限制时，任务不会自行失败。普通 `VideoJob` 的相关修复没有覆盖这个分支。

离线复现：chunk=100，假服务端每次返回 maximum is 100s，连续执行 10 次，全部返回 progress，`failed=False`、`retries=0`。从控制流可见，该条件持续成立时没有重试上限。

建议验收：首次学习新上限可以重排；相同上限持续拒绝必须有重试预算和明确失败结果。

### R07 — 勾选账号与课程加载、测速使用的账号不一致

位置：`guet/gui/web/index.html:329`、`:351`、`:369`、`:382`。

启动按 `state.picked` 选择账号，而 `loadCourses()` 和 `bench()` 始终取第一个 logged_in 账号；切换账号只重绘账号区，没有清空或重载课程。

静态确认的触发场景：A、B 均登录，A 排在前面；用户只选 B，刷新课程仍读取 A，启动却把 A 的课程 ID 交给 B。账号课程不同会导致不可访问课程、计划错误或启动失败；测速也可能针对错误账号。

建议验收：单选 B 后课程和测速都属于 B；多账号模式明确课程归属或交集规则，不直接共享首个账号的课程列表。

### R08 — planned 参数解析失败后 GUI 永久停在 running

位置：`guet/gui/server.py:390`、`:403`。

在 `state.begin('running')` 和账号/运行参数修改后才解析 planned；解析失败时线程尚未创建，也没有状态回滚。普通网页生成的是数字，此问题主要影响错误 API 请求或异常前端数据。

离线复现：合法 accounts/courses 配合 `planned='invalid'`，得到 ValueError；随后 `state.status == 'running'`，`state.run_thread is None`。后续启动被忙碌状态阻止，停止也没有 worker 可以执行 finish。

建议验收：完整校验必须先于运行状态改变；启动线程之前任一步失败都应恢复可启动状态。

### R09 — 实时取消遗漏未完成任务结果，并可能显示成功

位置：`guet/realtime.py:257`、`guet/scheduler.py:245`。

实时循环取消时直接 break，在跑和排队活动均未转为 pending，也没有 `_record()` 回调。调度器又把没有 failed 的结果视为成功，因此取消可以表现为“零失败、全部成功”。这与 tick 分支新增的取消收尾行为不一致。

离线复现：两个 300 秒任务、单车道，在第一次等待期间请求取消，返回结果数为 0，记录数为 0。取消标记在验证后已复位。

建议验收：取消应有明确的账号级终态，且在跑与排队任务均可追踪；不能仅凭没有 failed 判定全部完成。

### R10 — tick 等待不可中断，关闭窗口可能早于后台收尾

位置：`guet/ticker.py:149`、`guet/gui/app.py:144`。

tick 使用整段 `sleep(interval)`，只能醒来后检查取消；默认间隔可达 120 秒。GUI 退出只 join 后台线程 8 秒，而后台是 daemon 线程。若在 tick 等待开始后关闭窗口，等待窗口明显短于停止延迟，程序可能退出而未执行任务收尾和资源关闭。

证据为等待/取消/退出链路静态审查，本轮未等待真实 120 秒或关闭用户正在运行的 GUI。建议验收：停止能唤醒等待，退出确实完成预定清理；另应覆盖 `--no-window` 的独立退出分支，其当前提前 return，不经过通用 finally。

### R11 — 多账号进度分母取自首账号，无法反映各自计划

位置：`guet/gui/web/index.html:387`、`guet/gui/server.py:403`。

启动时只向 `accounts[0]` 查询计划，然后把一个 planned 数字复制给所有账号。即使所有账号拥有同一课程，各自已完成活动不同，剩余计划数也不同。例如 A 剩 10 项、B 剩 2 项，B 完成 2 项后分母仍是 10；反向情况可能超过分母。请求计划时也没有携带这次选择的目标百分比，进一步增加计划与执行不一致的可能。

此项为前后端数据流静态确认。建议验收：按账号取得与本次执行参数一致的计划，覆盖不同历史进度和低于 100% 的目标；达标跳过活动的统计口径也应一致。
